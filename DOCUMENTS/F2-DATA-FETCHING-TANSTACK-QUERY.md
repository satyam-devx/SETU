# F2 — Data Fetching / TanStack Query

## Scope

F2 moves SETU's server-state data fetching onto TanStack Query v5 while preserving the existing F1 compatibility boundary.

## Implemented

- TanStack Query `QueryClient` is now the canonical server-state cache.
- `QueryClientProvider` is mounted at the application root.
- Existing `src/hooks/useQuery.js` is now a thin compatibility wrapper over TanStack Query's `useQuery`.
- Existing `queryClientInstance` consumers are preserved through a compatibility adapter backed by the TanStack `QueryClient`.
- Request deduplication is delegated to TanStack Query's query cache/fetch lifecycle.
- Shared caching uses canonical `queryKeys`.
- Default stale time: 30 seconds.
- Default garbage-collection time: 10 minutes.
- Retry policy: up to 2 retries with exponential backoff capped at 3 seconds; client/auth/validation/conflict/not-found errors are not retried.
- Offline state is integrated with TanStack `onlineManager`, so retry attempts are paused while offline.
- Invalidation uses TanStack partial query-key matching.
- Active stale queries are refetched on network recovery.
- Query cancellation is wired through TanStack's `AbortSignal` and passed through the query boundary. Core product/order/address read APIs were additionally made signal-aware where their Supabase transport can consume the signal.
- Existing realtime cache writes and mutation invalidation continue to work through the compatibility adapter.

## Preserved compatibility

The following F1 APIs remain available while their implementation is now TanStack-backed:

- `queryClientInstance.getQueryData`
- `queryClientInstance.getQueryState`
- `queryClientInstance.setQueryData`
- `queryClientInstance.subscribe`
- `queryClientInstance.fetchQuery`
- `queryClientInstance.invalidateQueries`
- `queryClientInstance.removeQueries`
- `queryClientInstance.refetchInvalidated`
- `queryClientInstance.clear`

This avoids a risky all-at-once rewrite of realtime and legacy `useDataFetch` consumers.
